# Architecture

## Decision summary

The application uses a monorepo with four explicit boundaries:

1. `apps/web` owns interaction, browser persistence, and 3D rendering.
2. `packages/contracts` owns the current TypeScript project schema and demonstration data.
3. `services/api` owns HTTP validation/versioning and will expose analysis jobs in later phases.
4. `packages/engineering` owns pure numerical and geometry functions independently of HTTP and UI.

This separation prevents rendering code from becoming the source of physical results. Future solvers must live in the engineering package and expose typed diagnostics through the API.

## ADR-001: Browser-first editor, server-side analysis

**Status:** accepted.

Geometry editing and local JSON project management run in the browser for immediate feedback. Computational analyses will execute in Python because NumPy/SciPy, solver diagnostics, and independent tests are first-class requirements. No analysis result is generated by an animation.

## ADR-002: SI storage with presentation conversions

**Status:** accepted.

All persisted coordinates and dimensions use metres. The initial editor presents millimetres and converts only at its input boundary. API fields include unit declarations. See `COORDINATES_AND_UNITS.md`.

## ADR-003: Versioned JSON before database persistence

**Status:** accepted.

The current project format uses `schemaVersion: 1.0.0`, Zod validation in the web layer, and Pydantic validation at the API boundary. Browser local storage is a convenience, while JSON remains the portable source. A database is intentionally deferred until multi-user needs exist.

## ADR-004: Invalid transient edits remain inspectable

**Status:** accepted.

The editor may temporarily display invalid geometry so an engineer can repair it. Errors are highlighted and described; save/export is disabled until error-severity diagnostics are cleared. Imports with geometry errors are rejected atomically.

## Runtime flow

```text
JSON/local storage -> structural validation -> geometry diagnostics -> editor/viewport
                                                           |
                                                           +-> persistence allowed only if valid

future analysis request -> FastAPI -> engineering solver -> diagnostics + units + status
```

## Failure boundaries

- The React error boundary replaces an unrecoverable render failure with a reload action.
- Contract errors identify the invalid field and reject the whole import.
- Geometry errors identify affected hardpoints and block persistence.
- API errors use structured HTTP responses.
- Future nonlinear solvers must return non-convergence rather than a plausible-looking pose.
